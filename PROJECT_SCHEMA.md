# Your Business Planner — contractul actual

Actualizat la 27 octombrie 2026. Acest document descrie comportamentul curent; notele cronologice anterioare sunt in [istoricul pastrat](docs/PROJECT_SCHEMA_ISTORIC_2026-10-26.md). Istoricul nu defineste contracte alternative. Criteriile nevalidate pentru lansare sunt in [registrul de lansare](docs/ROADMAP_LANSARE.md), iar planul integral este in [planul de calitate](docs/PLAN_CALITATE_2026-10-26.md).

## Aplicatii si medii

- `business-api`: Laravel, MySQL, Bearer Sanctum pentru Android si sesiune web separata pentru operatorul platformei.
- `business-front`: React Native/TypeScript; local se foloseste aplicatia Android prin interfata ei.
- `company_id` izoleaza datele; `user_id` pastreaza autorul. `companies` este radacina. Identificatorii de business sunt UUID.
- Configuratia API este in `config/gt.php`, citita din mediu; clientul citeste `@env`. Credentialele SQL nu ajung in client.
- API-ul local este pe 8010; MySQL pe 3307, Mailpit web pe 8026. Porturile/configuratiile sunt ale mediului local, nu adrese de productie.

## Identitate vizuala

Logo-ul produsului este SVG-ul animat Gatify furnizat de utilizator, pastrat in `assets/brand` pe mobil si `public/brand` pe API. Loginul si antetele folosesc aceleasi forme si acelasi ciclu GT-GATIFY de 8 secunde, randat nativ prin SVG/Reanimated. Preferinta de reducere a miscarii afiseaza cuvantul complet; animatia este oprita in fundal. Panoul operatorului si paginile de recenzie folosesc assetul SVG local. Invitatiile HTML includ PNG-ul inline si o alternativa text. Iconitele Android/iOS, faviconul si ecranul nativ de pornire folosesc cadre statice derivate din acelasi logo. ## Identitate si autorizare

Rolurile companiei sunt `owner`, `admin`, `employee`. Operatorul are `is_platform_admin`, separat de companie; contul mobil al companiei nu autorizeaza panoul web.

Tokenurile au termen finit. Logout revoca sesiunea curenta si curata identitatea, navigarea, cache-ul privat, navigarea amanata, jurnalele private locale si reminderele. Resetarea parolei revoca toate tokenurile, iar schimbarea parolei invalideaza si sesiunile web existente. Cererile si callbackurile sunt legate de generatia sesiunii; o sesiune veche nu poate modifica sesiunea noua. Scrierile tokenului si ale jurnalelor sunt serializate.

Serviciile din `app/Domain` scopeaza accesul la compania curenta. Resursele altei companii intorc 404. Contul blocat sau profilul de angajat inactiv nu pastreaza accesul. Angajatul vede numai rezervarile si remuneratia alocate, fara financiarul companiei sau datele nepermise ale clientilor.

Compania suspendata, abonamentul expirat sau categoria indisponibila blocheaza datele inclusiv prin linkuri emise anterior. Functiile `staff`, `finance`, `documents`, `reminders` sunt autorizate pe server. Dezactivarea nu sterge istoricul. Clientul ascunde fluxurile indisponibile si invalideaza numai interogarile relevante; ascunderea nu constituie autorizare.

Accesul comercial/trial necesita inceputul perioadei atins si sfarsitul strict dupa timpul serverului. Perioada comerciala valabila are prioritate fata de trial. Ziua finala aleasa in panou este inclusa in Europe/Bucharest; in UTC se stocheaza limita exclusiva. Limita locurilor numara conturile neblocate si invitatiile nefolosite cu termen strict in viitor. Verificarea cresterii se face sub lockul companiei.

## Reguli temporale normative

1. Datele calendaristice si introducerea/afisarea programului folosesc Europe/Bucharest. Timestampurile sunt UTC si se expun ISO 8601 cu offset.
2. Intersectia intervalelor este semi-deschisa: `[start, end)`. O rezervare care se termina exact la 00:00 nu ocupa ziua urmatoare.
3. Pentru agenda si filtre, un program complet este viitor cat timp `ends_at > now`; la `ends_at <= now` este trecut, inclusiv egalitatea exacta.
4. Fara program complet, o rezervare blocanta ocupa intreaga sa zi locala, de la 00:00 inclus la urmatorul 00:00 exclus. Ziua curenta ramane viitoare pana la limita ei exclusiva.
5. Cererile `tentative` sunt in asteptarea avansului, fara termen si fara blocarea salii sau a personalului. Numai starile `confirmed` si `completed` ocupa intervalele; anularile si inregistrarile istorice `expired` nu blocheaza.
6. La confirmare sau finalizare se pastreaza si restrictia unei singure rezervari blocante pe aceeasi sala/data, chiar daca orele propuse nu se intersecteaza.
7. Orele inexistente la schimbarea orei sunt refuzate. Ora repetata necesita offset explicit +03:00 sau +02:00. Nu se reparseaza textul localizat produs de `toLocaleString`.
8. Serverul decide disponibilitatea si autorizarea. Ceasul telefonului actualizeaza prezentarea si solicita revalidare, fara a prelungi o sesiune sau un abonament.

Scrierile dependente sunt tranzactionale. Lockurile urmeaza companie → resursa; concurenta se verifica pe MySQL dedicat `_test`. SQLite nu demonstreaza lockurile MySQL. `companies.planner_revision` avanseaza explicit in tranzactiile planificatorului. `companies.availability_revision` este un contor separat, avansat atomic numai la scrierile rezervarilor si salilor. Importurile directe necesita scrieri oprite si `PlannerRevision::advance($companyId, availabilityChanged: true)` pentru rezervari/sali inaintea reluarii accesului. Migrarea adauga contorul cu valoarea initiala 1 inaintea noului cod API; rollbackul revine intai la codul anterior, apoi elimina numai contorul.

Versiunile rezervarii, platii, clientului, salii, documentului si personalului se verifica pe resursa recitita sub lock. O versiune veche produce `RESOURCE_VERSION_CONFLICT / 409`, fara suprascrierea datelor curente. Nu se reintroduce implicit o resursa arhivata.

Cheia de creare este persistata impreuna cu intentia canonica si resursa. Retry-ul identic recupereaza aceeasi resursa; o intentie diferita cu aceeasi cheie produce codul de conflict specific. In mod normal, primul refuz explicit de disponibilitate reda editarea; dupa un rezultat incert se pastreaza cheia si payloadul original pana la reconciliere.

## Contracte HTTP

Prefix `/api`. Raspunsurile private, inclusiv erorile, au `Cache-Control: no-store`. Datele de lista sunt paginatori Laravel cu `page` si `per_page`, limitat de `Controller::perPage()`. Cataloagele sunt marginite natural; istoricul nu este descarcat integral in client.

| Resursa | Endpointuri actuale si acces |
| --- | --- |
| Autentificare | POST login, password/forgot, password/reset, invitations/accept, cu throttle; GET me si POST logout pentru cont activ |
| Rezervari | GET events, events/{id}; POST/PUT/DELETE pentru owner/admin cu acces activ; angajatul citeste numai alocarile proprii |
| Calendar | GET calendar?date_from&date_to&hall_id&exclude_event_id; GET calendar/day?date&hall_id&include_inactive&page&per_page&snapshot; GET calendar/revision si POST calendar/realtime/auth (throttle 30/minut); owner/admin |
| Sali | GET/POST halls; GET/PUT/DELETE halls/{id}; POST halls/{id}/status; owner/admin |
| Clienti | GET/POST clients; GET/PUT/DELETE clients/{id}; GET clients-lookup?communication_channel&contact_value (throttle 60/minut); owner/admin |
| Personal | GET/POST employees; GET/PUT/DELETE employees/{id}; GET staff-availability; modul staff si owner/admin |
| Firma/conturi | GET company, team, invitations; PUT profile/company si POST company/fiscal-lookup; administrarea firmei si invitarile respecta rolul owner |
| Plati | GET/POST events/{eventId}/payments; GET/PUT/DELETE event-payments/{id}; modul finance si owner/admin |
| Documente | GET/POST events/{eventId}/documents; GET/PUT/DELETE event-documents/{id}; GET event-documents/{id}/download-url; modul documents |
| Sumar | GET overview, owner/admin si finance; interval cel mult 366 zile |
| Remindere | GET reminder-events, fereastra limitata si numai pentru drepturile contului si modulul reminders |
| Operare publica | GET health; numai status ok/unavailable si HTTP 200/503, fara detalii de DB/disc/joburi |
| Compatibilitate publica | GET mobile-policy; mod, min_build, recommended_build, contract_version si store_url HTTPS optional |
| Telemetrie | POST telemetry/errors, cont activ si throttle 10/minut; numai categorii/context tehnic validat, fara mesaj/payload privat |

POST/PUT events folosesc hall_id, date, type, status, starts_at, ends_at, expires_at, minimum_guests, estimated_guests, final_guests, child_guests, menu_price, child_menu_price, menu_name, agreed_advance, advance_due_at, extra_services, staff si notes. Identitatea clientului este fie client_id, pentru compatibilitatea cererilor existente, fie client_phone cu client_name optional; cele doua identitati nu se trimit impreuna. Telefonul se normalizeaza si se valideaza pe server. Un numar cunoscut refoloseste clientul companiei fara a-i suprascrie numele; un numar nou creeaza clientul si contactul in aceeasi tranzactie cu rezervarea, cu telefonul canonic drept nume daca numele este necompletat. Un client arhivat se restaureaza pastrand numele si istoricul. Lockul companiei si unicitatea contactului impiedica duplicatele concurente. Refuzul rezervarii anuleaza si crearea clientului. Amprenta operation_id normalizeaza telefonul si numele optional, iar amprentele istorice cu client_id se pastreaza. Crearea primeste operation_id, editarea version; identificatorii companiei si autorului nu vin din formular. extra_services este lista `{name, amount}`; staff este lista de alocari `{employee_id, job_role, pay_type, rate, starts_at, ends_at}`. Backendul calculeaza totalurile si costurile. Colectiile externe sunt validate inainte de conversie; obiectul JSON nu este acceptat in locul unei liste.

`GET events` include `meta.months` cu totalurile lunare complete ale filtrului si `meta.snapshot`. Pagina, totalul, amprenta, relatiile si totalurile lunare sunt citite intr-o tranzactie cu moment unic. Amprenta HMAC include revizia, identitatea/rolul, filtrele, marimea paginii, ziua locala si tranzitiile de incheiere indexate. Schimbarea paginarii produce `BOOKING_LIST_CHANGED / 409`; clientul reia prima pagina.

`GET calendar/day` expune pe sala id/name/capacity/minimum_guests/is_active si lista `bookings` cu id/status/type/starts_at/ends_at. Campurile booking_id/status/type/starts_at/ends_at de la nivelul salii pastreaza primul interval. Include toate intervalele care intersecteaza ziua, inclusiv continuari. O sala inactiva filtrata fara intervale apare ca inactive numai cu include_inactive=1. `meta.snapshot` se retransmite; schimbarea produce `CALENDAR_DAY_LIST_CHANGED / 409`. `meta.revision` identifica starea globala a calendarului la aceeasi citire.

`GET calendar` accepta optional `exclude_event_id` pentru alegerea datei la editare: rezervarea exclusa este verificata in compania curenta (404 pentru o resursa straina), apoi eliminata atat din numaratori, cat si din ocuparea zilelor. Filtrul `hall_id` si regulile intervalelor nocturne raman aplicate celorlalte rezervari. Identificatorul exclus trebuie sa fie UUID; structurile sau valorile invalide produc eroare de validare.

Sumarul calendarului contine `revision`, halls `{id,name,is_active}` si days `{date,confirmed,tentative,occupied_halls,active_capacity,active_occupied_halls,historical_occupied_halls,free}`. Ocuparea numara distinct sala–zi; confirmed/tentative numara inceputurile rezervarilor. `free` scade doar ocuparea activa din capacitatea activa. Statistica anuala nu inventeaza capacitate pentru sali inactive. Agregarile fiecarui raspuns sunt citite coerent sub lock comun al companiei; endpointurile distincte nu promit snapshot comun. `GET calendar/revision` intoarce numai `{revision}`: amprenta HMAC pentru compania si identitatea curenta, revizia scrierilor, ziua locala si tranzitiile de incheiere. Verificarea foloseste maximele indexate existente si nu incarca sau agrega listele rezervarilor. Raspunsurile raman private si no-store; revizia nu autorizeaza cereri si nu expune nume, sume sau identificatori ai rezervarilor.

## Bani si stari

Conditiile comerciale VENUE separa `estimated_guests` (meniuri estimate pentru adulti), `final_guests` (meniuri confirmate, optional), `child_guests` (meniuri copii, optional) si `child_menu_price`. Noile campuri sunt optionale in API pentru compatibilitate; numaratorile sunt intregi intre 0 si 100000 sau null, iar pretul copiilor este un sir monetar nenegativ. Pentru copii > 0 este obligatoriu un pret pozitiv; refuzul stabil este `BOOKING_CHILD_MENU_PRICE_REQUIRED / 422`. Valoarea contractului = max(minimum_guests, final_guests ?? estimated_guests ?? minimum_guests) × menu_price + (child_guests ?? 0) × child_menu_price + servicii suplimentare. Copiii nu contribuie la minimul adultilor. Zero confirmat este diferit de null si se supune minimului salii. Raspunsurile comerciale includ noile campuri numai pentru owner/admin; drepturile angajatului raman limitate la alocarile proprii.

`halls.menu_price` si `halls.child_menu_price` sunt preturi implicite optionale, decimal(12,2), expuse de GET/POST/PUT halls; se valideaza intre 0 si 99999999.99 si pot fi golite cu null. Rezervarea noua precompleteaza aceste preturi si minimul din sala, inclusiv daca lista salilor soseste dupa deschiderea formularului. Preturile rezervarii pot fi negociate. Refetch-ul nu suprascrie preturile sau estimarea editate. Actualizarea salii nu schimba conditiile rezervarilor existente. Pentru contractul nou cu estimated_guests, serverul stabileste minimum_guests exclusiv din sala blocata; la editarea aceleiasi sali pastreaza minimul istoric, iar mutarea foloseste minimul noii sali. Clientii vechi fara estimated_guests pastreaza minimul negociat la creare, cel putin minimul salii. Amprentele istorice si jurnalele fara noile campuri raman valide; amprenta noua canonizeaza campurile optionale si nu depinde de minimul read-only afisat.

Migrarea aditiva `2026_10_29_010000_add_menu_terms_and_hall_menu_prices` se aplica inaintea codului API si a aplicatiei mobile. Adauga preturile pe halls si estimarea/copiii/pretul copiilor atat pe events, cat si pe venue_booking_details. Nu inventeaza preturi de sala, nu modifica totalurile istorice si lasa numaratorile noi null. Scrierile celor doua reprezentari VENUE raman in aceeasi tranzactie. Rollbackul poate sterge coloanele numai inainte de folosirea lor; ulterior refuza cu `MENU_TERMS_ROLLBACK_REQUIRES_RECONCILIATION`, pentru a nu pierde date financiare. Dupa utilizare se aplica o migrare corectiva sau reconciliere/restaurare din backup coerent, impreuna cu versiunea compatibila a aplicatiei.

Calculele folosesc exclusiv bani intregi prin `App\Support\Money`; stocarea foloseste decimal, raspunsurile monetare folosesc siruri zecimale. Tariful maxim este 999.999,99, iar totalul maxim 99.999.999,99. Costul duratelor si soldul derivat sunt limitate inaintea salvarii si a produselor care pot depasi intervalul. Overflow-ul produce `BOOKING_AMOUNT_TOO_LARGE` sau `BOOKING_BALANCE_TOO_LARGE / 422`, cu rollback integral.

Sold = contract − incoming completed + outgoing refund completed. Celelalte cheltuieli nu micsoreaza artificial datoria clientului. Platile pending/cancelled nu intra in aceasta formula. Retry-ul unei plati nu dubleaza resursa sau auditul. Corectia/anularea cere versiunea actuala. Auditul financiar pastreaza numai campurile permise, fara notele brute.

Stari rezervare: tentative, confirmed, completed, cancelled, expired. Stari plata: pending, completed, cancelled. Galeria si documentele nu declara fisierul sters fizic pana la confirmare/absenta.

## Fisiere private si galerie

URL-urile de descarcare sunt temporare, semnate si legate de sesiunea emitenta; nu includ tokenul Bearer. Descarcarea revalideaza sesiunea, contul, rolul, compania, abonamentul si modulul. URL-ul semnat complet este confidential si nu este logat.

Galeria rezerva durabil metadatele in hall_images inaintea scrierii fisierului. hall_id poate fi null, iar deleted_at viitor este lease de 15 minute. Rezervarile nepublicate raman private si consuma cota. Publicarea si purgerul blocheaza compania; o rezervare curatata nu mai poate fi publicata (`HALL_IMAGE_UPLOAD_EXPIRED / 422`). Cleanup-ul confirma file_deleted_at numai dupa stergere/absenta. Rollback-ul la hall_id obligatoriu refuza fisiere pendinte necuratate.

## Ecrane, recuperare si accesibilitate

Toate formularele mobile folosesc `shared/hooks/useAppForm`, care pastreaza momentul initial al validarii si revalideaza automat campurile deja in eroare cand se modifica datele. Regula acopera validarile declansate prin Continuare/trigger, submit, actualizarile programatice, selectiile, datele, orele, campurile din liste si conditiile dependente. O valoare inca invalida ramane marcata; o valoare corectata pierde automat mesajul si conturul rosu. Reevaluarile sunt serializate, iar o schimbare aparuta in timpul validarii determina o noua evaluare a ultimei valori. Erorile globale nu sunt sterse prin editarea unui camp; erorile de tip server se revalideaza local numai dupa schimbarea campului vizat. Exceptiile neasteptate din reevaluare ajung la reportError, fara datele formularului.

Campurile obligatorii afiseaza `*` la finalul etichetei, prin proprietatea `required` a componentelor comune. Marcajul nu se dubleaza pe etichetele istorice care au deja asterisc. Campurile optionale raman fara marcaj; obligativitatea conditionata urmareste starea curenta a formularului (programul rezervarii, meniuri copii, date fiscale, contactul istoric si alocarile evenimentului). Numarul de telefon este obligatoriu pentru rezervarile noi; numele clientului nou ramane optional. Controalele de text si data anunta si caracterul obligatoriu prin indiciul accesibil. Tipul documentului si fisierul nou primesc etichete explicite. Validarea si contractele serverului raman sursa regulilor acceptate la salvare.

Pasul Conditii comerciale foloseste Meniuri estimate (adulti), cu Minimul salii afisat informativ imediat dedesubt, fara input editabil. Meniuri confirmate este optional, cu indicatia orientativa de aproximativ 7 zile inaintea evenimentului, fara termen impus. Denumirea meniului ramane separat ca Meniu ales (optional). Un panou distinct Meniuri copii contine numarul optional si pretul pentru copii; avansul are propriul panou. Serviciile suplimentare au fiecare card cu titlu numerotat, denumire, valoare si actiune accesibila de eliminare; cheia formularului este stabila la stergere. Recapitularea, detaliile, compararea conflictelor si textul pregatit pentru distribuire disting estimarea, confirmarea, minimul adultilor si copiii. Formularul salii configureaza separat pretul meniului pentru adulti si pentru copii, iar sumarul salii le afiseaza sau indica lipsa configurarii. Layoutul foloseste tokenurile existente si permite font marit si derulare cu actiunile principale vizibile.

Butoanele comune text, icon si multiline urmaresc durata actiunii: afiseaza spinner in stanga textului (sau in locul iconitei pentru butoanele fara text), expun busy/disabled si blocheaza imediat apasarile repetate pana la terminare. Spinnerul ramane in stanga inclusiv cand iconita normala este in dreapta. Actiunile asincrone returneaza promisiunea; operatiunile cu stare explicita de salvare, incarcare sau deschidere a formularului transmit acea stare. Cardurile de actiuni si reincercarile din bannere folosesc acelasi mecanism. La succes sau esec, butonul se reactiveaza; erorile nepreluate sunt afisate prin showError. Rezultatele actiunilor dintr-o sesiune veche nu pot modifica loaderul sau afisa erori in sesiunea noua. Confirmarile asincrone pastreaza dialogul deschis cu spinner pe confirmare, dezactiveaza celelalte actiuni si se inchid dupa terminare. Actiunile locale sincrone se termina imediat, fara o intarziere artificiala.

Formularele de creare a rezervarilor si platilor asteapta citirea jurnalului criptat inainte de a deschide modalul final. Incarcarea foloseste indicatorul din ecran, fara un modal temporar care sa fie demontat si redeschis pentru editor. Editarea rezervarilor nu asteapta jurnalul unei creari. Erorile de recuperare raman vizibile si blocheaza crearea pana la reusita citirii; recuperarea operatiunilor incerte si protectia impotriva duplicatelor se pastreaza. Celelalte formulare de adaugare/editare pastreaza un singur cadru modal pe durata deschiderii si actualizarilor de date.

Pasul Sala si program afiseaza data o singura data si selectoare separate pentru Ora de inceput si Ora de sfarsit. Alegerea orei deschide un dialog compact cu campuri numerice pentru ora 00-23 si minutul 00-59, grila de ore si butoane rapide de minute la 5 minute. Alegerea orei trece automat la minute; confirmarea aplica valoarea, iar inchiderea pastreaza valoarea precedenta. Se poate introduce orice minut, fara lista lunga de ore. O actiune separata goleste ora. Orele si secundele istorice neschimbate sunt pastrate la editare. Daca sfarsitul nu este dupa inceput in aceeasi zi, se muta automat in ziua urmatoare; egalitatea inseamna aceeasi ora in ziua urmatoare. Selectorul si explicatia indica a doua zi. Schimbarea datei reface timestampurile pastrand orele; schimbarea orei de inceput recalculeaza ziua sfarsitului, iar golirea inceputului goleste ambele ore. Orele inexistente la trecerea la ora de vara nu se pot confirma; ora repetata necesita alegerea explicita a primei sau celei de-a doua aparitii. API-ul continua sa primeasca starts_at/ends_at UTC, iar momentele istorice neschimbate se pastreaza exact.

La rezervare noua, data minima este ziua curenta din Europe/Bucharest. O deschidere pornita dintr-o data istorica foloseste cel mai devreme ziua curenta. Calendarul dezactiveaza zilele trecute si navigarea spre lunile anterioare lunii curente, inclusiv prin gesturi. Schema frontend si POST events refuza crearea in trecut; API-ul intoarce VALIDATION_FAILED cu BOOKING_DATE_IN_PAST pentru campul date. Editarea unei rezervari existente pastreaza accesul la istoric. Repetarea aceleiasi operatii deja confirmate ramane idempotenta si dupa trecerea zilei; exceptia nu permite crearea unei alte rezervari in trecut. Regula limiteaza ziua, fara a interzice orele anterioare din ziua curenta.

Pasul Client al rezervarii foloseste un dialog compact adaptat continutului, cu plafonul de inaltime si comportamentul tastaturii pastrate de cadrul comun. Porneste de la un singur camp Numar de telefon, cu tastatura telefonica si cautare exacta dupa normalizarea internationala. GET clients-lookup nu creeaza date, verifica separat compania contactului si a clientului si intoarce matched/client/events_count/suggestion; matricea Bearer, rolul owner/admin, abonamentul si no-store raman obligatorii. Cautarea este temporizata la 400 ms, anulabila si izolata prin companie/telefon in cache; un raspuns intarziat nu poate afisa alt client. Incarcarea este explicita, iar eroarea ofera reincercare si blocheaza continuarea pana la verificare. Clientul cunoscut apare intr-un card compact. Pentru un numar nou apare Numele clientului (optional); se poate continua cu numarul, fara crearea anticipata a clientului si fara un buton separat Client nou. Schimbarea efectiva a numarului goleste numele optional; reformatarea aceluiasi telefon il pastreaza. Recapitularea foloseste numele cunoscut, numele optional sau telefonul. Editarea cu telefon neschimbat pastreaza client_id si istoricul rezervarii. Jurnalul criptat pastreaza payloadul telefonic original si continua sa citeasca recuperarile vechi bazate pe client_id. Textele despre fusul orar apar numai la pasul Sala si program. Nu este necesara o migrare; backendul compatibil se livreaza inaintea clientului mobil.

Starea tentative este afisata ca In asteptarea avansului. Explicatia starii apare imediat sub dropdownul Stare rezervare ca mesaj informativ compact, cu iconita informativa, text secundar de 12 si spatiu de 24 pana la campurile de ora; foloseste tokenurile existente ale temei si permite marirea fontului. ## Compatibilitate mobila

Clientul trimite X-App-Build si X-App-Platform; acestea nu autorizeaza cereri. APP_BUILD din fisierul de mediu selectat este si versionCode Android. ENVFILE selecteaza acelasi mediu pentru Babel/Gradle; buildul release foloseste .env.production implicit. Cache-ul Metro include amprenta fisierului de mediu, pentru a separa aplicatia de business de E2E. Schimbarea fisierului cere restart Metro. Valorile nevalide opresc buildul Android.

Politica publica are modurile observe/recommend/enforce. Implicit este observe, min/recommended 0. Mai multe afiseaza recomandarea de actualizare cand exista un build recomandat mai nou si un URL verificat. Blocarea se activeaza numai dupa publicarea buildului compatibil si validarea URL-ului de actualizare. `MOBILE_POLICY_ENABLED` activeaza citirea anticipata; un CLIENT_UPDATE_REQUIRED primit activeaza verificarea chiar daca rolloutul anticipat era oprit.

In enforce, scrierile incompatibile ale companiei primesc 403 cu `CLIENT_UPDATE_REQUIRED`, fara a fi confundate cu abonamentul sau un 401. me/logout si citirile autorizate raman disponibile. Ecranul de actualizare pastreaza jurnalele; deconectarea explicita avertizeaza ca elimina datele locale. Un endpoint absent pe API-ul vechi nu produce singur o blocare, iar un esec offline nu confirma disparitia unei blocari cunoscute.

## Erori, monitorizare si operare

Backendul intoarce coduri stabile in `error.code`; frontendul detine textul romanesc cu diacritice si fallbackul. Toate erorile afisate trec prin showError, mesajele prin showMessage si confirmarile prin confirmAction. Nu se afiseaza mesajul brut al backendului.

Codurile curente includ UNAUTHENTICATED, SESSION_INACTIVE, FORBIDDEN, RESOURCE_NOT_FOUND, VALIDATION_FAILED, TOO_MANY_REQUESTS, SERVER_ERROR; SUBSCRIPTION_INACTIVE, CATEGORY_UNAVAILABLE, COMPANY_ACCESS_DENIED, MODULE_DISABLED; RESOURCE_VERSION_CONFLICT, BOOKING_OPERATION_CONFLICT, PAYMENT_OPERATION_CONFLICT, CLIENT_OPERATION_CONFLICT; HALL_ALREADY_BOOKED, EMPLOYEE_ALREADY_ASSIGNED; BOOKING_LIST_CHANGED, CALENDAR_DAY_LIST_CHANGED; CLIENT_UPDATE_REQUIRED. Maparea completa este in shared/api/apiError.ts, iar regulile requesturilor definesc codurile de validare specifice.

X-Request-ID accepta numai UUID; alte valori sunt inlocuite. Identificatorul se intoarce si se pastreaza in ApiError, inclusiv pentru raspunsuri invalide. reportError nu trimite mesaje arbitrare, payloaduri, URL-uri, note, telefon sau credentiale; 409/422, reteaua si timeouturile asteptate nu devin incidente critice. Cu MONITORING_ENABLED=true, API-ul colecteaza numai categoria, sursa, statusul, request_id si buildul validat. Livrarea catre serviciul extern si alertele cer configurarea mediului.

Canalele de logare folosesc lista explicita de evenimente/context tehnic; mesajele arbitrare si exceptiile brute sunt redactate inainte de handler. Pentru o exceptie se pastreaza tipul, numele fisierului si linia, fara mesaj, argumente sau query. Logurile de acces optionale descriu ruta sablon, nu URL-ul sau query-ul utilizatorului.

Schedulerul urmareste separat inceputul, succesul/esecul si durata pentru deliver-mail, purge-documents si purge-hall-images. Comanda expire-bookings a fost eliminata; cererile fara avans nu expira automat. `php artisan business:health --json` expune numai operatorului CLI starea DB, storage, joburilor si backlogului agregat. GET health expune doar starea minima. Pragurile initiale configurabile sunt 180 secunde heartbeat, 300 secunde email pending si 900 secunde cleanup restant; nu sunt SLA demonstrate.

`business:backup --with-files --quiesced` necesita mentenanta si oprirea declarata a scrierilor; in testing ramane obligatorie declaratia de quiescenta. Creeaza SQL si copii private ale fisierelor referite, inclusiv cele arhivate, cu manifest/checksumuri si numerele tuturor tabelelor. Uploadurile viitoare fara continut sunt marcate separat. `business:verify-recovery` verifica integritatea; `--compare-database` compara numere numai intr-o baza restaurata testing/MySQL/_test. Nu importa SQL si nu certifica restaurarea. Procedura, criptarea externa si limitele sunt in `docs/RECUPERARE_SI_DEPLOY.md`.
